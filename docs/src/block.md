# Block Lifecycle

A `Block` is the runtime's unit of execution. It wraps a user-defined `Kernel`
with infrastructure for message dispatch, port management, and lifecycle
control.

## The Block Trait

```rust
#[async_trait]
pub trait Block: Send + Any {
    // Identity
    fn id(&self) -> BlockId;
    fn instance_name(&self) -> Option<&str>;
    fn set_instance_name(&mut self, name: &str);
    fn type_name(&self) -> &str;
    fn is_blocking(&self) -> bool;

    // Stream ports
    fn stream_input(&mut self, name: &str) -> Option<&mut dyn BufferReader>;
    fn connect_stream_output(
        &mut self, name: &str, reader: &mut dyn BufferReader,
    ) -> Result<(), Error>;

    // Message ports
    fn message_inputs(&self) -> &'static [&'static str];
    fn connect(
        &mut self, src_port: &PortId,
        sender: Sender<BlockMessage>, dst_port: &PortId,
    ) -> Result<(), Error>;

    // Execution
    fn inbox(&self) -> Sender<BlockMessage>;
    async fn run(&mut self, main_inbox: Sender<FlowgraphMessage>);
}
```

This trait is object-safe (with `async_trait`), which allows `dyn Block` to be
used for dynamically loaded plugins.

## WrappedKernel

Every block in the flowgraph is actually a `WrappedKernel<K>`:

```rust
pub struct WrappedKernel<K: Kernel> {
    pub meta: BlockMeta,
    pub mio: MessageOutputs,
    pub kernel: K,
    pub id: BlockId,
    pub inbox: mpsc::Receiver<BlockMessage>,
    pub inbox_tx: mpsc::Sender<BlockMessage>,
}
```

- **`meta`**: Instance name and other metadata.
- **`mio`**: Message output ports with their connected destinations.
- **`kernel`**: The user-defined kernel struct.
- **`inbox` / `inbox_tx`**: MPSC channel for receiving `BlockMessage`s from the
  runtime and other blocks.

`WrappedKernel<K>` implements `Block` by delegating to the kernel's
`KernelInterface` methods (generated by `#[derive(Block)]`).

It also implements `Deref<Target = K>` and `DerefMut`, so you can access the
kernel's fields and methods directly through a `BlockRef`.

## Lifecycle States

A block goes through four states during its lifetime:

```
  Created  →  Initialized  →  Running  →  Shutdown
```

### 1. Created

The kernel is constructed and wrapped in `WrappedKernel::new()`. Stream ports
are initialized with their block ID and inbox sender. The block is registered
in the flowgraph but not yet running.

### 2. Initialized

The runtime sends `BlockMessage::Initialize`. The block calls
`kernel.init(&mut mio, &mut meta)`, which lets the kernel perform one-time
setup (opening files, allocating resources, etc.). The block reports back to
the flowgraph with `FlowgraphMessage::Initialized`.

### 3. Running

The block enters its main work loop, alternating between processing messages
and calling `kernel.work()`.

### 4. Shutdown

When `work_io.finished` is set to `true` (by the kernel or by a
`BlockMessage::Terminate`), the block:

1. Notifies all connected stream ports that it's done
2. Calls `kernel.deinit(&mut mio, &mut meta)` for cleanup
3. Sends `FlowgraphMessage::BlockDone` to the runtime

## The Work Loop

The `run_impl` method implements the main event loop:

```
loop {
    ┌─ 1. Drain messages (non-blocking) ──────────────┐
    │   Notify         → (no-op, just wake up)        │
    │   Call           → kernel.call_handler(port, p)  │
    │   Callback       → same, but send response back  │
    │   StreamInputDone  → mark input as finished      │
    │   StreamOutputDone → set work_io.finished        │
    │   Terminate      → set work_io.finished          │
    │   BlockDescription → return port metadata        │
    └─────────────────────────────────────────────────┘
                         │
    ┌─ 2. Check shutdown ─┘
    │   if finished → notify ports, deinit, send BlockDone, return
    └─────────────────────────────────────────────────┘
                         │
    ┌─ 3. Handle blocking ┘
    │   if work_io.block_on is Some → select(inbox, future)
    │   if inbox message → process it, loop back to 1
    │   if future completes → clear block_on, continue
    └─────────────────────────────────────────────────┘
                         │
    ┌─ 4. Call work() ────┘
    │   kernel.work(&mut io, &mut mio, &mut meta)
    │   if !call_again → yield, then wait for Notify
    └─────────────────────────────────────────────────┘
}
```

### Message Dispatch

Messages are processed non-blockingly via `try_recv` on the inbox. This means
the block never blocks waiting for a message when there's `work()` to do.

`BlockMessage::Call` invokes a message handler (fire-and-forget).
`BlockMessage::Callback` does the same but sends the return value back through
a oneshot channel.

### The `work_io.block_on` Mechanism

A kernel can set `work_io.block_on = Some(future)` in its `work()` method to
suspend until an external event completes (e.g., waiting for hardware). The
work loop uses `futures::future::select` to race the future against incoming
inbox messages, so the block remains responsive.

### The `call_again` Flag

After `work()` returns, if `work_io.call_again` is `false`, the block yields
and waits for the next `BlockMessage::Notify` before calling `work()` again.
Buffer producers send `Notify` when new data is available, so blocks only wake
up when there's something to process.

## BlockMessage and FlowgraphMessage

Communication between blocks and the runtime uses two message enums:

### BlockMessage (runtime → block)

| Variant | Purpose |
|---------|---------|
| `Initialize` | Start the block's init sequence |
| `Terminate` | Request graceful shutdown |
| `Notify` | Wake up the work loop (new data available) |
| `Call { port_id, data }` | Fire-and-forget message handler call |
| `Callback { port_id, data, tx }` | Message handler call with response |
| `StreamInputDone { input_id }` | Upstream finished producing |
| `StreamOutputDone { output_id }` | Downstream finished consuming |
| `BlockDescription { tx }` | Introspection query |

### FlowgraphMessage (block → runtime)

| Variant | Purpose |
|---------|---------|
| `Initialized` | Block completed initialization |
| `BlockDone { block_id }` | Block finished normally |
| `BlockError { block_id }` | Block finished with error |
| `BlockCall / BlockCallback` | Forwarded from `FlowgraphHandle` |
| `Terminate` | Shutdown all blocks |
| `FlowgraphDescription / BlockDescription` | Introspection |

## Blocking Blocks

Blocks marked with `#[blocking]` run their `work()` method on a dedicated
thread (via `spawn_blocking`) rather than on the async executor. This is for
blocks that perform long-running synchronous I/O (e.g., reading from hardware)
that would starve other async tasks.
